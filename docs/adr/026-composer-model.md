# ADR 026: Composer modes, state and extension seams

`chat_composer` is described by three orthogonal slots (header, panel,
actions) filled from a host-built `ComposerSpec`. Its controller owns input
only. Its text controller keeps entities in sync with edits and produces a
neutral rich-text value. It knows neither the panel nor any inset arbiter.

## Decided

| Area | Decision |
| ---- | -------- |
| Mode model | Three slots, not one growing enum. **Header** is what sits above the field (reply, edit, forward, link preview, suggestion) with a priority rule. **Panel** is what occupies the input row, chosen by a host-supplied resolver (default text panel; recording; recorded preview; restricted, join and unblock sibling panels). **Actions** is a data list of `ActionDescriptor` (id, semantic icon, placement leading or trailing, enabled and visible, `active` for the on state of a toggle, tap handler, and an optional `wrap` that builds a host widget around the rendered button so the host can add a hover region or a probe without the composer knowing it) for emoji toggle, attach, mic or send, scheduled, silent, bot menu and slow mode. The composer owns slots, layout and animation; the host owns what fills them. The sealed idle, editing and replying mode and the hard-coded buttons are deleted. |
| State owner | Declarative. The host builds `ComposerSpec(header, panel, actions, enabled, busy)` and passes it to the widget, which animates between specs. `ComposerController` owns input only: entity-aware text, focus, selection, input queries, field scroll and height, and the commands `insertContent`, `insertText`, `backspace` and `clear`. Reply and edit begin-commands, stored ids and preview strings stay with the host. |
| Text model | `ComposerTextController` (a `TextEditingController` subclass over `RichText`) keeps plain text and entity spans in sync with edits and renders inline content through the asset cache. It is the only text controller of the composer. It exposes the neutral rich-text value, plain text plus entities (offset, length, kind), used for drafts, send and edit-load. Entity kinds: inline content ref, bold, italic, code, strike, underline, spoiler, quote, link, mention, username, hashtag, list item (opt-in, below), code block with an optional language ([ADR 033](033-code-blocks-in-rich-text.md)). The model is flat text with ranged entities permanently; quotes, code blocks and list items are line-widening entities, not nodes. Entity edits commit on finished IME composition. |
| Formatting commands | A closed set on `ComposerTextController`, one to one with `EntityKind`: toggle a style (bold, italic, underline, strike, spoiler, code, quote), toggle a code block, apply or remove a link, clear formatting, and `isActive` / `canApply` queries. Each is a replacement of the selection's slice, so line widening, exclusivity (code excludes other styles) and merging stay `RichText`'s. Selection-only: a collapsed caret disables them except applying a link (inserts the URL as linked text) and the line-widening kinds (act on the caret's line). There is no typing style, because no reference client has one and it makes entity edits on IME commit ambiguous. The commands are text-model operations, not `ComposerController` commands. Shortcuts are Intents and Actions bound to Telegram Desktop's set, with both `meta` and `control` activators, overridable through the shortcut map of [ADR 031](031-localization-accessibility-and-input.md); one code path with the menu. |
| Selection menu | `ComposerSelectionMenu`, owned by `chat_composer` and mounted through the editable's menu builder on every platform, not the platform selection menu extended. It is a two-page swipe-back card. The main row holds the clipboard actions the field offers (Cut, Copy, Paste, Paste as plain text while the composer has a rich clipboard, Select all) and a More button; the actions that do not fit the row (it is at most `min(400, width - 32)` wide; a button stays while it fits beside the 56 dp More button, and the last item of the whole menu may take that room, as `FloatingToolbar.layoutMainPanelItems` does) go to the top of the More page, above the formatting actions. A main-row button is its label between 16 dp each side (24 at the row's first start and, with no More button, at its last end), 48 dp wide and tall at least; the More button is 56 by 48 flush with the card's end, its icon 24 and its ripple 20 dp. The More page is as wide as its widest row (18 dp each side, measured on one line, so no label is ellipsized or wrapped; at least as wide as its Back row; at most the screen less 32), a list of 42 dp tiles in a box of its rows counted at 48 dp, four at most and two at least by the room, with half a row more when it has more and then it scrolls (16 dp fades at both edges, 4 dp above the first row), and a 48 dp Back row (arrow at 16, label at 56, 16 dp regular) at the end nearer the selection (under the list when the card is above it) whose top edge is a one-device-pixel hairline; the whole card is 264 dp at most. The page slides in over 300 ms on the CSS ease cubic (the main row slides left by half its width, shrinks to 0.95 and is dimmed, the page enters from the right, the card's size blends between the two pages), a drag to the right over the open page follows the finger and a fling of 600 dp/s or more closes it, and while a turn runs further opens and closes are ignored. The card fades in over 150 ms; after an action, Escape or Back it fades out over 220 ms with a 5 dp drift away from the selection, its rows frozen as they were. Scroll and out-of-view fades belong to the editable's toolbar wrapper (one linear 150 ms fade that also takes the card out of hit testing); the open page survives them. It sits above the selection when 264 dp fit there, else below, else on the roomier side, 8 dp from the selection above it and 20 dp below it, 16 dp from the screen's sides and 12 from the safe area and the keyboard, centred on the selection's endpoints (not the pointer); the page keeps one edge of the row still as it opens (the trailing edge, the leading one in right-to-left). Labels are 14 dp medium (the theme's label-large family, no letter spacing) in the text token, the Back label 16 dp regular, the card Material elevation 3 at radius 12; Material icons only (`more_vert`, `arrow_back`). Its options come from `ComposerSpec.formatting`, its labels from the strings scope ([ADR 031](031-localization-accessibility-and-input.md)): Cut, Copy, Paste and Select all from `ChromeStrings.editMenu` (the pointer menu's group, so both menus speak the app's language), Paste as plain text from `ChromeStrings.composer`, the rest from `ChromeStrings.formatting`; none from `MaterialLocalizations`, its link prompt from `ComposerSpec.linkPrompt` (the host's dialog, given the current URL) and its back priority from `ComposerSpec.backPriority`; colours are `SelectionMenuTokens` and the motions are the `menuEnter`, `menuLeave` and `menuPage` roles of `chrome_foundation`, so reduce-motion reaches all three. Formatting order on the page: Bold, Italic, Underline, Strikethrough, Monospace, Spoiler, Quote, Code block, Link (and Remove link while the selection touches one), then with lists on Bullet list and Numbered list, then Clear formatting; each shows its own effect (Bold in bold, Monospace in a monospaced face, a list row a bullet or a number before its label). Date and highlight are not items. After an action the menu closes and the selection collapses to a caret at its extent on every platform; Select all keeps it open and a link prompt keeps the selection until it is answered. Back closes the whole menu from either page. |
| Pointer menu | Under `ComposerMenuPolicy$Desktop` (`ComposerMenuPolicy.forPlatform`: macOS, Windows, Linux and the web; `$Mobile` on touch platforms) a secondary click in the field opens the **pointer menu**: the reference desktop client's context menu of its message field, `Ui::PopupMenu` with the plain style. The popup is `PointerMenu` in `chrome_foundation` ([ADR 027](027-foundation-theme-glass-motion.md)), because the shared look, rows, hints, submenus and keyboard model are also what the message popup needs and `chat_composer` may not depend on `panel_pages` ([ADR 020](020-package-topology.md)); `chat_composer` owns the rows (`ComposerPointerMenuItems`, a pure function of the text controller and a `ComposerMenuState`), the hints (`ComposerMenuHints`, per platform) and the opening (`ComposerPointerMenu`). The editable reports the click through `ExtendedTextField.onSecondaryClick` and leaves the caret and selection alone ([ADR 038](038-composer-editable-fork.md), divergence K); the field takes focus on the press, and the menu opens on the edge `ComposerMenuPolicy$Desktop.opensOn` names. It opens at the pointer (body 5 px from it, flipped and pushed in to stay inside the overlay), modal for the pointer and the keyboard, with the selection kept painted because the menu is a child of the field's focus node. After a row the menu is closing and the field has focus before the row runs; the selection is untouched (Select All selects and closes). The Menu key and Shift+F10 (`ShowComposerMenuIntent`, bound by the desktop shortcut policy) open it at the caret's lower left. The floating toolbar stays for touch (a long press on a touch screen) and under `$Mobile`. |
| Pointer menu rows | Top to bottom: Spelling (see below), Undo, Redo, separator, Cut, Copy, Paste, Paste as plain text (an addition, only while the composer has a rich clipboard), Delete, separator, Formatting, separator, Select All; Spelling moves to the bottom after a separator when the menu will open upward. Every row is always present and greyed when it cannot apply: Undo and Redo by the field's history, Cut, Copy and Delete by a non-empty selection, Paste by a paste probe (`ComposerController.canPaste`: text, or media an `onPastedMedia` host takes), Select All by a non-empty text. Formatting is always live and holds: Bold, Italic, Underline, Strikethrough, Quote, Monospace, Spoiler, then the additions Code block and, with lists on, Bullet list and Numbered list, a separator, Create link or Edit link (Edit when the selection touches a link, or, with nothing selected, when the pointer is over one; Remove link, an addition, follows it), a separator and Clear formatting. Style rows are live when there is a selection and `canApply`; at a caret **every** style row is greyed, the line kinds (Quote, Code block, lists) included, to match the reference (the commands still accept a caret for the keys); Create link stays live. A row whose option `ComposerSpec.formatting` does not offer is absent. Hints are the reference keys in the platform's native form (`Ctrl+Z` and `⌘Z`; Redo `Ctrl+Y` on Windows, `Ctrl+Shift+Z` on Linux, `⇧⌘Z` on macOS; Delete and the additions have none). Labels are `ChromeStrings.editMenu` with Qt's `&` mnemonics, drawn underlined. **Spelling** is a seam: `ComposerSpec.spellChecker` (`ComposerSpellChecker`); the composer ships no checker and draws no squiggles. With one, the menu asks it about the word under the pointer (not a number, a link, a mention, code, a username or a hashtag) before it opens and shows Add to Dictionary, Ignore word and the suggestions for a wrong word, or Remove from Dictionary for a right word the user added; a right word with nothing to offer adds no row. The reference's Manage dictionaries row is omitted (it appears only for a non-system checker). |
| Pointer menu divergences | What is not the reference, and why. **Chosen, not read:** Date is omitted (no formatted-date entity); the Unicode control character submenu is omitted; Code block, the list rows, Remove link and Paste as plain text are workspace additions placed after Spoiler, after Paste, and after Edit link (Telegram has none; no "1:1" exists for them); the popup clamps to the overlay, not the screen (a Flutter overlay cannot leave the window); the text uses the theme's font and the clamped text scale 1.3 where the reference uses Open Sans; the keyboard-opened menu's position is the caret's lower left; the window losing focus closes the menu (`AppLifecycleState`); every key is swallowed while it is open. **Divergence from the platform toolkit:** a secondary click does not select the word on macOS (the reference toolkit ignores the right button in its text control; stock Flutter selects it). **Unverified, one named constant each, flagged in code:** the row height 33 (`PointerMenuMetrics.rowHeight`: 8 + the 13 px font line height 18 + 7; the 18 is derived from the Open Sans metrics and not measured); the shadow blur mapping (`shadowBlur` 5 as a Gaussian sigma of 2.5; the reference blurs with a box-ish kernel); the arrow stroke width 1.5 (the arrow is a mask in the reference); the mouse guard distance 10 px (`mouseGuardDistance`: the toolkit's default drag distance); which click edge opens the menu per OS (`ComposerMenuPolicy$Desktop.platformsOpeningOnPress`, macOS and Linux on the press, Windows on the release); the macOS glyph form of the hints and the toolkit's rule that omits a hint the application registered; whether the toolkit's own translations are loaded; the clipboard probe timeout (`PointerMenuTiming.clipboardProbe` 300 ms, after which Paste counts as live); Control+Click on macOS (not mapped). **Verified and ported:** the radius 8, padding 8, widths 156 to 300, text at 17, hint gap 6, 13 px text, 11 px separators, the open animation (200 ms, width 0.5 to 1 over 0.6 and height 0.3 to 1 over 0.9 of the clock on `easeOutCirc`, opacity over 0.3, a revealing strip 20% high), the 150 ms linear fade out, the 300 ms submenu aim hold, the 650 and 200 ms ripple, the guard of 6 motions, the keyboard model (Down and Up wrap and skip rows that cannot be chosen, Right and Left for submenus, Enter and Space, Escape closes a submenu then the menu, nothing selected on open). The aim triangle (apex follows the pointer while it stays inside; the hold ends 300 ms after it last moved there) is the port's reading of the reference's description. |
| Selection menu deviations | Where the menu is not the plain card above, and why. **A formatting item that cannot apply is greyed, not hidden:** it keeps its place on the page at the tile's disabled look (label at 0.38, no tap), so the page keeps its shape from one selection to the next. Quote alone is left out, over a selection that is quoted already (the menu has no way to unquote). **A collapsed caret gets the page too:** the line kinds (Quote, Code block) and Link are enabled, the rest greyed, because the composer has no typing style (see Formatting commands). **Link** is one row, Create or Edit by whether the selection touches a link, and Remove link while it does; the host's `ComposerLinkPrompt` gets the current URL. **Additions** with no earlier counterpart: Quote, Code block, the list rows, and Paste as plain text (on the row if it fits, else first on the page); their copy and cut and paste go through the composer's rich clipboard when it has one. **Text scale** is clamped to 1.3 (the clamp the shell's fixed-height controls use, [ADR 031](031-localization-accessibility-and-input.md)) because the rows are fixed-height. **Keyboard:** Tab from the field moves focus into the menu, which is a child of the field's own focus node so the editable keeps its toolbar; Tab, Shift+Tab and the arrows move between items (only the page that shows is traversed), Enter chooses and Escape closes. **Semantics:** every item is a button with its label, `selected` when the selection already has it, and enabled state; the hidden page is not spoken. **Colours** are tokens, not the ambient theme: the fill is the palette's raised surface, the text its on-surface colour, the divider its separator at half opacity (a host wanting Material's own look builds its palette from its colour scheme, `ChromePalette.fromColorScheme`), the shadow black at 0.45, the page dim black at `0x18` on a light palette and `0x40` on a dark one. **The clipboard labels are the host's `ChromeStrings.editMenu` strings** with the pointer menu's `&` access marks removed (`PointerMenuLabel.parse`), on every platform: the previous menu read `MaterialLocalizations`, which an app without a delegate for its own language answers in English, so the clipboard rows came out in English beside formatting rows in the app's language. **Fit, traced to `FloatingToolbar.java`:** row height 48 (415), padding 16 (1418) and 1.5 times that at the row's outer ends (1025), minimum width 48 (1416), More button 56 by 48 (442) reserved as the row's end padding (1045), width limit `min(400, viewport - 32)` (949-957), label 14 dp medium (1424-1425) with no ellipsis on the page (1468), page rows 42 (1417), 18 dp padding (1384), width the widest row (1088, 1133-1141), height `rows * 48 + 48 + peek` with 2 to 4 rows by the room (1143-1150), list padding 4 / 2 (1205), edge fade 16 dp (1295-1345), Back row 48 with its label at 56 and 16 dp (446-477), a hairline of `1 / density` at its top (476). **Where the port keeps its own:** the swipe-back page turn, the 150 / 220 ms enter and leave and the dim are the message menu's mechanism, not the morph of the composer's `FloatingToolbar`; the card is elevation 3 on token colours, not elevation 1 on the theme's keys; the formatting items stay on the More page, where the reference sorts them into the main row too; the reference lets a page grow past the screen and clips its label, here the page stops 16 dp short of the screen's sides and only then ellipsizes, and it is never narrower than its Back row (the reference cuts "Back" on a page of short rows); the Back row's divider is the card's top edge when Back is above the list, as in the reference, so only a Back under the list is set off by it. There is no tooltip on the More button (a `Tooltip` under the editable's follower asserts, flutter/flutter#178522). The card does not hide while the selection moves; it follows it. |
| Lists | Opt-in: `ComposerTextController(lists: true)`, default false. A list item is one `EntityKind` entity per item, widening to its lines like a quote but never merging with neighbours; numbers are derived at encode time, not stored; styles inside items are allowed, code blocks and quotes on the same lines are not. With lists on: typed markers (`- `, `* `, `1. ` plus space at a line start) become items; Enter continues or ends an empty item; Backspace at an item start outdents then ends it; Tab and Shift+Tab change depth (0 to 3); Shift+Enter is a soft break; pasting two or more marker lines as plain text makes items; a gutter draws the markers and speaks them (one semantics node per marker, labelled from the formatting strings). There is no list-specific undo. A composer-local list attribute outside `RichText` was rejected: two models for one text. |
| Form field | `ComposerFormField` puts the composer's one field in a host's form: a `FormField<RichText>`, as `TextFormField` is a `FormField<String>`, whose value is `ComposerController.richText`, whose validator and `onSaved` read it and whose `reset` restores the text it was built with. Around the text is the host's `InputDecoration` (label, hint, helper, borders, the validator's error); inside is the island's field: entities, lists, the selection and pointer menus, the rich clipboard, the soft keyboard and the formatting keys of the platform's shortcut policy without submit and header dismissal (Enter is a newline in a form). It takes what a spec carries for the island as its own parameters (`formatting`, `linkPrompt`, `backPriority`, `spellChecker`) and `maxLength`, the length budget's unit (code points of the plain text): the decoration counts `length/maxLength` and past it the counter and the border take the error colour, as a stock field with an unenforced `maxLength` does; nothing is trimmed or refused, so a host that must not save over the budget says so in its validator. One widget over the field's state, not an export of `ComposerSelectionMenu`, the list gutter and `listMarkers`: those stay internal, so the menu cannot be mounted on another editable and the gutter's contract with the editable stays private. The field is one state with two layouts (`ComposerFieldLayout` island or form); only the chrome differs. |
| Editable | `composer_editable` is the one editable: the composer field renders through it on every platform, with Material selection handles. No stock `TextField` fallback ([ADR 038](038-composer-editable-fork.md)). |
| Paste report | `ComposerController` reports each paste that puts text into the field to `onPaste` as `ComposerPaste(range, text, wasRich)`: the range is where the text landed (after any widening over an atom), `text` the plain text, `wasRich` whether the clipboard's rich form was used. The callback is a constructor field like `onPastedMedia`, not a signal, because a paste is an event with a payload and one consumer. Only pastes through the `RichClipboard` are reported; without one the platform's paste reaches the controller as an edit and is not told from typing. The host decides whether to offer applying markdown formatting to a plain paste and applies it with `replaceRange`; the offer is feedback UI and stays app-side ([ADR 032](032-rich-clipboard.md)). |
| Length budget | `ComposerSpec.messageLengthLimit` (nullable: null is no limit) is a code-point budget of the plain text (`ComposerController.length`, `plain.runes.length`), set by the host from its server configuration ([ADR 034](034-rich-text-wire-and-persistence.md)). The view draws the remaining count under the row once **100 or fewer** remain (`ComposerLengthCounter.visibleFrom`, close enough that the user wants to know) and, while the count is negative, refuses the primary action and the submit key: the host's `onTap` is not called and the counter shakes (no shake under instant motion). Another send path, such as a scheduled send, checks `length` itself. Nothing is trimmed and no markdown delimiter is counted. |
| Send path | `ComposerController.sendableText` is `richText` with every mention the host did not resolve in this draft rewritten to `Username(name)` (`downgradeUnresolvedMentions`; a mention whose text is not an `@name` loses its entity and keeps its text). A mention is resolved when it came in through `replaceQuery` (picked), `restore` (loaded for edit or from a draft) or `trustMention`, or when the host's `confirmMention` accepts its id; a paste brings none. The host encodes `sendableText`, not `richText`, with `RichTextMarkdown.encode`. `clear` and `restore` forget the draft's trust. The composer does no other step of the send: skipping the trim of an emoji-only message stays the host's. |
| Drafts | A draft is the markdown string the wire carries ([ADR 034](034-rich-text-wire-and-persistence.md)): the host writes `RichTextMarkdown.encode(richText)` to its `KeyValueStore` debounced on change, keyed by chat id with the edited message's id beside it, clears it on send, and `restore(RichTextMarkdown.decode(markdown))` loads it. `richText` and `restore` are lossless for every entity kind, pinned by a contract test over a corpus. The composer ships no store helper: the key scheme is the host's. |
| Suggestions | The composer exposes the active token as a `ValueListenable` (`package:listen`) input query (kind, text, replace range, caret anchor rect) and `replaceQuery(...)`. Query kinds are an open, host-registered set (trigger plus rule). The host builds mention, hashtag, command and inline-emoji panels. |
| Extent | The composer publishes its own height as data; the host feeds it, with presentation occupancy, into the viewport bottom padding ([host insets](../architecture/14-host-chrome-insets.md)). The composer imports no inset types. |
| IME | An input option `softKeyboard: auto or suppressed` plus focus commands. Hand-off choreography with the panel belongs to presentation ([ADR 028](028-panel-presentation.md)). The composer does not use `SystemChannels` to coordinate with the panel. |
| Units | Island shell (glass), header slot (reveal animation), field (entity input, height animation), action slots, panel resolver. The bottom fade stays with the composer. The emoji-face icon resolver is deleted: the host sets the action's semantic icon. |
| Panel link | The composer does not know the panel. The emoji toggle is an action whose icon the host derives from presentation visibility and the shell's selected page. |

## Why

- Telegram iOS splits an accessory panel (a resolver), alternative input panels (sibling nodes plus a resolver) and accessory items (a data list). Android uses `fieldPanelShown`, recording ints and priority bit-flags. Desktop uses separate member controls plus `ComposeFeatures`. Text is entity-bearing everywhere, and suggestions and mentions live outside the composer unit everywhere.
- The old `ChatEnterView` mixed row UI, IME policy, panel-open suppression keyed on icon state and custom render boxes. The header banner existed twice: as a widget and as a sealed mode.

## Rejected

| Alternative | Why not |
| ----------- | ------- |
| Extending the sealed mode; per-mode strategy objects bundling header, panel and actions | Modes multiply; the slots vary independently |
| Plain controller with placeholder characters; host-owned text model | Entities would drift from the text; every host reimplements sync |
| Suggestion panels built into the composer; no query abstraction | Suggestion sources are host data |
| Controller-owned mode state with commands; a both-ways facade | Two owners for one state |
| Extending the platform selection menu with formatting items | The Android platform menu is not what the reference client ships; its formatting UI is its own floating toolbar |
| A typing style (formatting that applies to the next typed text) | No reference client has one, and it makes entity edits on IME commit ambiguous |
| Exporting `ComposerSelectionMenu`, the gutter hooks and `listMarkers` for a form host to assemble its own field | Every host would rebuild the field's wiring (clipboard routing, the menu's tear-off builder, the gutter's room and semantics, the soft keyboard re-attach), and the internals would become contract |
| The rich-text value in its own package or inside the composer package | `content_model` already holds the inline ref, and bodies need the value without the composer |

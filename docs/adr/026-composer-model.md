# ADR 026: Composer modes, state and extension seams

`chat_composer` is described by three orthogonal slots (header, panel,
actions) filled from a host-built `ComposerSpec`. Its controller owns input
only. Its text controller keeps entities in sync with edits and produces a
neutral rich-text value. It knows neither the panel nor any inset arbiter.

## Decided

| Area | Decision |
| ---- | -------- |
| Mode model | Three slots, not one growing enum. **Header** is what sits above the field (reply, edit, forward, link preview, suggestion) with a priority rule. **Panel** is what occupies the input row, chosen by a host-supplied resolver (default text panel; recording; recorded preview; restricted, join and unblock sibling panels). **Actions** is a data list of `ActionDescriptor` (id, semantic icon, placement leading or trailing, enabled and visible, `active` for the on state of a toggle, tap handler, and an optional `wrap` that builds a host widget around the rendered button so the host can add a hover region or a probe without the composer knowing it) for emoji toggle, attach, mic or send, scheduled, silent, bot menu and slow mode. The composer owns slots, layout and animation; the host owns what fills them. The sealed idle, editing and replying mode and the hard-coded buttons are deleted. |
| State owner | Declarative. The host builds `ComposerSpec(header, panel, actions, enabled, busy)` and passes it to the widget, which animates between specs. `ComposerController` owns input only: entity-aware text, focus, selection, input queries, field scroll and height, and the commands `insertContent`, `insertText`, `backspace` and `clear`. Reply and edit begin-commands, stored ids and preview strings stay with the host. |
| Text model | `ComposerTextController` (a `TextEditingController` subclass over `RichText`) keeps plain text and entity spans in sync with edits and renders inline content through the asset cache. It is the only text controller of the composer. It exposes the neutral rich-text value, plain text plus entities (offset, length, kind), used for drafts, send and edit-load. Entity kinds: inline content ref, bold, italic, code, strike, underline, spoiler, quote, link, mention, username, hashtag, list item (opt-in, below), code block with an optional language ([ADR 033](033-code-blocks-in-rich-text.md)). The model is flat text with ranged entities permanently; quotes, code blocks and list items are line-widening entities, not nodes. Entity edits commit on finished IME composition. |
| Formatting commands | A closed set on `ComposerTextController`, one to one with `EntityKind`: toggle a style (bold, italic, underline, strike, spoiler, code, quote), toggle a code block, apply or remove a link, clear formatting, and `isActive` / `canApply` queries. Each is a replacement of the selection's slice, so line widening, exclusivity (code excludes other styles) and merging stay `RichText`'s. Selection-only: a collapsed caret disables them except applying a link (inserts the URL as linked text) and the line-widening kinds (act on the caret's line). There is no typing style, because no reference client has one and it makes entity edits on IME commit ambiguous. The commands are text-model operations, not `ComposerController` commands. Shortcuts are Intents and Actions bound to Telegram Desktop's set, with both `meta` and `control` activators, overridable through the shortcut map of [ADR 031](031-localization-accessibility-and-input.md); one code path with the menu. |
| Selection menu | `ComposerSelectionMenu`, owned by `chat_composer` and mounted through the editable's menu builder on every platform, not the platform selection menu extended. It is a two-page swipe-back card. The main row holds the clipboard actions the field offers (Cut, Copy, Paste, Paste as plain text while the composer has a rich clipboard, Select all) and a More button; the actions that do not fit the row (it is at most `min(400, width - 24)` wide, the More button's 46 dp kept free) go to the top of the More page, above the formatting actions. The More page is 150 dp wide, a column of 42 dp tiles with a Back tile at the end nearer the selection (under the list when the card is above it) and a 1 dp divider between; a longer list scrolls inside a box of exactly the room, up to 320 dp over the whole card. The page slides in over 300 ms on the CSS ease cubic (the main row slides left by half its width, shrinks to 0.95 and is dimmed, the page enters from the right, the card's size blends between the two pages), a drag to the right over the open page follows the finger and a fling of 600 dp/s or more closes it, and while a turn runs further opens and closes are ignored. The card fades in over 150 ms; after an action, Escape or Back it fades out over 220 ms with a 5 dp drift away from the selection, its rows frozen as they were. Scroll and out-of-view fades belong to the editable's toolbar wrapper (one linear 150 ms fade that also takes the card out of hit testing); the open page survives them. It sits above the selection when 320 dp fit there, else below, else on the roomier side, 8 dp from the selection above it and 20 dp below it, 12 dp from the screen's edges, centred on the selection's endpoints (not the pointer); the page keeps one edge of the row still as it opens (the trailing edge, the leading one in right-to-left). Rows are 42 dp, labels the theme's body-large at 16 sp, the card Material elevation 3 at radius 12; Material icons only (`more_vert`, `arrow_back`). Its options come from `ComposerSpec.formatting`, its labels from the strings scope ([ADR 031](031-localization-accessibility-and-input.md)), its link prompt from `ComposerSpec.linkPrompt` (the host's dialog, given the current URL) and its back priority from `ComposerSpec.backPriority`; colours are `SelectionMenuTokens` and the motions are the `menuEnter`, `menuLeave` and `menuPage` roles of `chrome_foundation`, so reduce-motion reaches all three. Formatting order on the page: Bold, Italic, Underline, Strikethrough, Monospace, Spoiler, Quote, Code block, Link (and Remove link while the selection touches one), then with lists on Bullet list and Numbered list, then Clear formatting; each shows its own effect (Bold in bold, Monospace in a monospaced face, a list row a bullet or a number before its label). Date and highlight are not items. After an action the menu closes and the selection collapses to a caret at its extent on every platform; Select all keeps it open and a link prompt keeps the selection until it is answered. Back closes the whole menu from either page. |
| Selection menu deviations | Where the menu is not the plain card above, and why. **A formatting item that cannot apply is greyed, not hidden:** it keeps its place on the page at the tile's disabled look (label at 0.38, no tap), so the page keeps its shape from one selection to the next. Quote alone is left out, over a selection that is quoted already (the menu has no way to unquote). **A collapsed caret gets the page too:** the line kinds (Quote, Code block) and Link are enabled, the rest greyed, because the composer has no typing style (see Formatting commands). **Link** is one row, Create or Edit by whether the selection touches a link, and Remove link while it does; the host's `ComposerLinkPrompt` gets the current URL. **Additions** with no earlier counterpart: Quote, Code block, the list rows, and Paste as plain text (on the row if it fits, else first on the page); their copy and cut and paste go through the composer's rich clipboard when it has one. **Text scale** is clamped to 1.3 (the clamp the shell's fixed-height controls use, [ADR 031](031-localization-accessibility-and-input.md)) because the rows are fixed-height. **Keyboard:** Tab from the field moves focus into the menu, which is a child of the field's own focus node so the editable keeps its toolbar; Tab, Shift+Tab and the arrows move between items (only the page that shows is traversed), Enter chooses and Escape closes. **Semantics:** every item is a button with its label, `selected` when the selection already has it, and enabled state; the hidden page is not spoken. **Colours** are tokens, not the ambient theme: the fill is the palette's raised surface, the text its on-surface colour, the divider its separator at half opacity (a host wanting Material's own look builds its palette from its colour scheme, `ChromePalette.fromColorScheme`), the shadow black at 0.45, the page dim black at `0x18` on a light palette and `0x40` on a dark one. The clipboard labels are Material's on every platform. There is no tooltip on the More button (a `Tooltip` under the editable's follower asserts, flutter/flutter#178522). The card does not hide while the selection moves; it follows it. |
| Lists | Opt-in: `ComposerTextController(lists: true)`, default false. A list item is one `EntityKind` entity per item, widening to its lines like a quote but never merging with neighbours; numbers are derived at encode time, not stored; styles inside items are allowed, code blocks and quotes on the same lines are not. With lists on: typed markers (`- `, `* `, `1. ` plus space at a line start) become items; Enter continues or ends an empty item; Backspace at an item start outdents then ends it; Tab and Shift+Tab change depth (0 to 3); Shift+Enter is a soft break; pasting two or more marker lines as plain text makes items; a gutter draws the markers and speaks them (one semantics node per marker, labelled from the formatting strings). There is no list-specific undo. A composer-local list attribute outside `RichText` was rejected: two models for one text. |
| Editable | `composer_editable` is the one editable: the composer field renders through it on every platform, with Material selection handles. No stock `TextField` fallback ([ADR 038](038-composer-editable-fork.md)). |
| Paste report | `ComposerController` reports each paste that puts text into the field to `onPaste` as `ComposerPaste(range, text, wasRich)`: the range is where the text landed (after any widening over an atom), `text` the plain text, `wasRich` whether the clipboard's rich form was used. The callback is a constructor field like `onPastedMedia`, not a signal, because a paste is an event with a payload and one consumer. Only pastes through the `RichClipboard` are reported; without one the platform's paste reaches the controller as an edit and is not told from typing. The host decides whether to offer applying markdown formatting to a plain paste and applies it with `replaceRange`; the offer is feedback UI and stays app-side ([ADR 032](032-rich-clipboard.md)). |
| Length budget | `ComposerSpec.messageLengthLimit` (nullable: null is no limit) is a code-point budget of the plain text (`ComposerController.length`, `plain.runes.length`), set by the host from its server configuration ([ADR 034](034-rich-text-wire-and-persistence.md)). The view draws the remaining count under the row once **100 or fewer** remain (`ComposerLengthCounter.visibleFrom`, close enough that the user wants to know) and, while the count is negative, refuses the primary action and the submit key: the host's `onTap` is not called and the counter shakes (no shake under instant motion). Another send path, such as a scheduled send, checks `length` itself. Nothing is trimmed and no markdown delimiter is counted. |
| Send path | `ComposerController.sendableText` is `richText` with every mention the host did not resolve in this draft rewritten to `Username(name)` (`downgradeUnresolvedMentions`; a mention whose text is not an `@name` loses its entity and keeps its text). A mention is resolved when it came in through `replaceQuery` (picked), `restore` (loaded for edit or from a draft) or `trustMention`, or when the host's `confirmMention` accepts its id; a paste brings none. The host encodes `sendableText`, not `richText`, with `RichTextMarkdown.encode`. `clear` and `restore` forget the draft's trust. The composer does no other step of the send: skipping the trim of an emoji-only message stays the host's. |
| Drafts | A draft is the markdown string the wire carries ([ADR 034](034-rich-text-wire-and-persistence.md)): the host writes `RichTextMarkdown.encode(richText)` to its `KeyValueStore` debounced on change, keyed by chat id with the edited message's id beside it, clears it on send, and `restore(RichTextMarkdown.decode(markdown))` loads it. `richText` and `restore` are lossless for every entity kind, pinned by a contract test over a corpus. The composer ships no store helper: the key scheme is the host's. |
| Suggestions | The composer exposes the active token as a `ValueListenable` (`package:listen`) input query (kind, text, replace range, caret anchor rect) and `replaceQuery(...)`. Query kinds are an open, host-registered set (trigger plus rule). The host builds mention, hashtag, command and inline-emoji panels. |
| Extent | The composer publishes its own height as data; the host feeds it, with presentation occupancy, into the viewport bottom padding ([host insets](../architecture/14-host-chrome-insets.md)). The composer imports no inset types. |
| IME | An input option `softKeyboard: auto or suppressed` plus focus commands. Hand-off choreography with the panel belongs to presentation ([ADR 028](028-panel-presentation.md)). The composer does not use `SystemChannels` to coordinate with the panel. |
| Units | Island shell (glass), header slot (reveal animation), field (entity input, height animation), action slots, panel resolver. The bottom fade stays with the composer. The emoji-face icon resolver is deleted: the host sets the action's semantic icon. |
| Panel link | The composer does not know the panel. The emoji toggle is an action whose icon the host derives from presentation visibility and the shell's selected page. |

## Why

- Telegram iOS splits an accessory panel (a resolver), alternative input panels (sibling nodes plus a resolver) and accessory items (a data list). Android uses `fieldPanelShown`, recording ints and priority bit-flags. Desktop uses separate member controls plus `ComposeFeatures`. Text is entity-bearing everywhere, and suggestions and mentions live outside the composer unit everywhere.
- The old `ChatEnterView` mixed row UI, IME policy, panel-open suppression keyed on icon state and custom render boxes. The header banner existed twice: as a widget and as a sealed mode.

## Rejected

| Alternative | Why not |
| ----------- | ------- |
| Extending the sealed mode; per-mode strategy objects bundling header, panel and actions | Modes multiply; the slots vary independently |
| Plain controller with placeholder characters; host-owned text model | Entities would drift from the text; every host reimplements sync |
| Suggestion panels built into the composer; no query abstraction | Suggestion sources are host data |
| Controller-owned mode state with commands; a both-ways facade | Two owners for one state |
| Extending the platform selection menu with formatting items | The Android platform menu is not what the reference client ships; its formatting UI is its own floating toolbar |
| A typing style (formatting that applies to the next typed text) | No reference client has one, and it makes entity edits on IME commit ambiguous |
| The rich-text value in its own package or inside the composer package | `content_model` already holds the inline ref, and bodies need the value without the composer |

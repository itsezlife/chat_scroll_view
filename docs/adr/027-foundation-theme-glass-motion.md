# ADR 027: Foundation theme tokens, glass and motion

`chrome_foundation` is a leaf package holding the semantic palette, per-component token groups, a required nestable theme scope, named glass materials with a quality policy, motion roles and a stock icon registry. It has no dependency on composer, panel or data code.

**Status**: Accepted  
**Date**: 2026-10-16  
**Amended**: 2026-10-18 — the pointer menu: `PointerMenu` (the shared desktop popup), `PointerMenuTokens` as a theme group (`ChromeThemeData.pointerMenu`, with the reference's day and night colours as presets), the motion roles `pointerMenuShow` and `pointerMenuHide`, `EaseOutCirc`, `PointerMenuTiming`, and `ChromeStrings.editMenu`; 2026-11-09 (native-media ticket 108) — the sampled glass keeps a capture while nothing under its region changed, and culls the capture to the region (row *Glass capture*); 2026-11-09 (native-media ticket 109) — the reference frosted look per material, refraction an opt-in, the capture saturated and snapped to a grid, no shader on the frosted path (rows *Glass look*, *Glass capture*, *Glass seam*); 2026-11-10 (native-media ticket 140) — the chrome face (row *Typography*)  
**Relates to**: [ADR 020](020-package-topology.md), [ADR 031](031-localization-accessibility-and-input.md)

## Decided

| Area | Decision |
| ---- | -------- |
| Token structure | A small semantic `ChromePalette` (surface, onSurface, accent, separator, destructive, placeholder, ...) with light, dark and custom constructors. Per-component token groups derive from it by default: `ComposerTokens`, `PanelTokens`, `GlassMaterials`, `ActionTokens`, and so on. Each group is immutable with `copyWith` and `lerp`, and individually overridable. The panel catalog theme (adapted in `panel_pages`) and the glass style derive from the same palette, so there is one brightness mechanism. |
| Delivery | `ChromeThemeScope` (an `InheritedModel`) in foundation. Lookup asserts without a scope, with no silent light fallback. Scopes nest: a per-chat or per-surface scope overrides only the groups it supplies. The scope animates between two themes through `lerp`. It is independent of `ThemeData`, with an optional adapter from `ColorScheme`. |
| Glass seam | `GlassSurface(material: ...)` with named `GlassMaterials` (composer island, panel button, top panel, ...) inside an optional `GlassSourceScope`. A host-provided `GlassQuality` policy (full liquid, frosted, flat, off) combines detected capabilities (Impeller shader availability, web and desktop support), a host lite-mode flag and the transient route-motion rule. An internal strategy chain (sampled liquid, sampled frost, `BackdropFilter`, flat fill) is not public API. The default quality is frosted; refraction (full liquid) is the host's opt-in. Only refraction needs a fragment shader: the frosted paths (a drawn capture, or a blur and saturation scene filter) need none, so a refracting surface draws frosted until its shader loads and for good if it fails to. Glass and its three shaders live in foundation. |
| Glass look | Frosted: the content behind the glass at an eighth of device resolution, blurred by a 40 dp radius (sigma 0.57735 r + 0.5 device px), saturation x3, under the material's tint at 0.76. Refracting: a quarter of device resolution, a 6 dp radius, saturation x3, tint at 0.85, rim refraction (intensity 0.75, index 1.5, rim 11 dp clamped to a fifth of the shorter side). Flat: the tint opaque, except while only route motion holds a filtered glass flat. The opacity belongs to the look, not the theme: tokens carry the opaque tint, the edges and the shadow per material (`GlassMaterialTokens.fromPalette`: island and buttons on `surface`, top panel on `surfaceDim`). Corners, edge widths and shadow geometry are `GlassMaterial` constants (island 22, 0.5, blur 1 at 1/3; button 18, 0.5, blur 11/3 at 2/3; top panel 0, 0.55). |
| Glass capture | A sampled glass renders the region of the glass source behind it (plus the refraction and blur reach), snapped out to a 2 image px grid, into a small image blurred and saturated at that size, shared per frame by nearby surfaces of one look (resolution, blur, saturation). The grid keeps a capture's size and pixel phase while a surface moves by less than a step. The capture is clipped to that region inside the blur, so the source outside it is culled from the display list. It is kept across frames while nothing under the region changed: the source's composited layer tree is diffed against the last frame's (picture identities, layer properties, structure), and a change recaptures only the regions it reaches, bounded by the repaint boundary that holds it. A region that moves or resizes, a layer type the diff does not read, and a playing texture under the region recapture every frame. Content painted outside its repaint boundary's paint bounds is not seen by the diff. |
| Motion | A `ChromeMotion` token group by semantic role (list transition 250 ms with the Android cubic, panel slide, search, header reveal, press, fade, presentation open and close, ...). Components read roles and hold no literal durations. A scope-level speed factor, including instant, implements reduce-motion and lite mode. |
| Pointer menu | `PointerMenu.show(context, globalPosition:, entries:, tokens:, motion:, focusParent:, returnFocusTo:)` opens the reference desktop client's popup list in the root overlay and returns a handle. Entries are `PointerMenuItem` (id, label with `&` mnemonic, hint, enabled, `onSelected`, optional submenu) and `PointerMenuSeparator`; a row that cannot be chosen is shown greyed. Placement, the open animation, the aim triangle and the arrow-key navigation are pure and public (`PointerMenuPlacements`, `PointerMenuReveal`, `PointerMenuAim`, `PointerMenuNavigation`); the geometry is `PointerMenuMetrics`, each value marked verified, derived or UNVERIFIED. Colours are `PointerMenuTokens` (`fromPalette`; `referenceDay` and `referenceNight` are the reference's own); the motion is two roles (a 200 ms clock whose width, height and opacity curves are fractions of it, and a 150 ms linear fade) so reduce-motion reaches it, and three literal timings (`PointerMenuTiming`: the 300 ms aim hold, the 650 and 200 ms ripple, the 300 ms clipboard probe bound) that are holds, not motion. It is a leaf concern: it knows no composer and no data. |
| Metrics | Telegram-derived geometry stays component-owned as documented constants. Only colours, materials and motion are tokens. |
| Typography | Not a token group. The face is the host's: `ChromeTypography.of(context)` is its Material theme's body family, fallback and size at the regular weight, not inheriting, so chrome placed outside a `Material` (overlay entries, popup routes) never draws in the framework's debug style. Each chrome text sets the size and weight its reference gives; Android's `bold()` is weight 500 (Roboto Medium). |
| Icons | A stock `ChromeIcon` registry (semantic id to painter) with a morph-transition helper; the `morphnext` dependency is isolated in foundation. Hosts register painters for custom ids. Composer actions and panel tabs refer to icons by semantic id. |
| Strings | Labels are never tokens. See [ADR 031](031-localization-accessibility-and-input.md). |
| Palettes | Telegram-derived light and dark palettes ship as defaults and apply only when supplied explicitly. |
| Wallpaper | Tokens are independent of wallpaper. A per-chat theme is a nested scope, and the host feeds the glass source from chat content. |
| Fallback matrix | The per-platform glass fallback (Impeller, web, Android, Windows, Linux) is established by capability detection and device testing, and is not decided here. |

## Why

- The old chrome colours were one flat 28-colour class with a silent light fallback, and three independent theming mechanisms (colours, patched catalog theme, glass style).
- Telegram Android uses key groups with fallback chains and a per-chat `ResourcesProvider` with animating colours; glass is a separate module with named presets chosen by capability and lite mode. iOS uses an immutable theme group tree and a one-entry glass update. No client has a central motion registry; role-based motion generalises the common practice.
- Glass cost is dominated by capture-based sampling shared per frame, and flat paint while a route moves avoids it.
- The look is the reference Android client's frosted glass (blur by downscale plus a residual blur, saturation x3, a solved tint opacity, per-surface edges and shadow); its refraction is shown only when the host asks, as the reference shows it only on the newest backends and behind a lite-mode flag.
- A merged capture per look already makes one capture for the island, the panel and the floating buttons over one chat, so the per-host atlas of disjoint slots was not taken; nor was a separately captured static backdrop, since the wallpaper is one shader draw in each capture and the layer diff keeps a capture while it is still.
- A capture per composited frame cost more on the raster thread than the frame itself on an idle screen whose only motion lay outside every glass; a diff of the layer tree is tens of layers on the UI thread.

## Rejected

| Alternative | Why not |
| ----------- | ------- |
| One flat token class; a flat key map with fallback chains | Cannot be overridden per component or nested cheaply |
| Flutter `ThemeExtension`; an explicit theme parameter on every widget | Ties chrome to `ThemeData`; prop drilling |
| A public `GlassRenderer` interface; public flag-driven glass widgets | Strategy details would become API |
| One atlas texture per scope with a slot per disjoint region; a declared static backdrop textured once | Nearby regions already merge into one capture; the backdrop is a single draw inside it. Revisit if a host frosts distant surfaces (top and bottom bars) that change together |
| Caller-passed transitions; component-owned motion constants | No global speed scale |
